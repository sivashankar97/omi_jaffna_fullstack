# OMI Jaffna backend CRUD

Base URL: `http://localhost:4000/api`. The frontend proxy also supports `/api` at `http://localhost:5173`.

Sign in with `POST /auth/login` using `{ "identifier": "admin email or Father ID", "password": "…" }` and retain the HttpOnly session cookie. Email login is limited to CMS staff roles (`admin`, `editor`, `publisher`); Father ID login is limited to `father` accounts. Father accounts can register through `POST /auth/register`; public registration only creates `father` accounts and does not verify Father IDs against an approved list. Existing local credentials are in `LOCAL-LOGIN.txt`.

Fathers sign in on the public site with their Father ID and password, can read their own account through `GET /auth/me`, and update their name, date of birth, email, mobile number or password through `PATCH /auth/profile`. Father ID and role cannot be changed by the account holder. Admins sign in with email and password to access the CMS. Admins can manage Father accounts through the team-account endpoints.

## Resources

| Resource | Create | List / Read one | Update | Delete |
| --- | --- | --- | --- | --- |
| All 13 content categories | `POST /items` | `GET /items?type=page`, `GET /items/:id` | `PUT` or `PATCH /items/:id` | `DELETE /items/:id` |
| Contacts | `POST /contacts` | `GET /contacts`, `GET /contacts/:id` | `PUT` or `PATCH /contacts/:id` | `DELETE /contacts/:id` |
| Enquiries | `POST /inquiries` | `GET /inquiries`, `GET /inquiries/:id` | `PUT` or `PATCH /inquiries/:id` | `DELETE /inquiries/:id` |
| Media assets | `POST /assets` (multipart `file`) | `GET /assets`, `GET /assets/:id` | `PUT` or `PATCH /assets/:id` | `DELETE /assets/:id` |
| Team accounts | `POST /users` | `GET /users`, `GET /users/:id` | `PUT` or `PATCH /users/:id` | `DELETE /users/:id` |
| Settings | `POST /settings` | `GET /settings`, `GET /settings/:key` | `PUT /settings/:key` | `DELETE /settings/:key` |

`PUT` supplies the full editable record, with defaults applied to optional fields. `PATCH` changes only supplied fields. For accounts, omitting `password` retains the existing password. Settings PUT retains its existing upsert behavior and replaces the whole `value` object. Media updates edit metadata; upload a new asset to replace file contents.

Single-record responses use `{ "item": ... }`; accounts use `{ "user": ... }`. Lists use `{ "items": [...] }`, except settings, which use `{ "settings": { ... } }`. Successful deletion returns `{ "ok": true }`. Creates return HTTP 201; malformed requests return 400, unauthenticated requests 401, disallowed operations 403, missing records 404, and duplicate/conflicting operations 409.

Supported settings keys: `site_identity`, `navigation`, `social_links`, `seo_defaults`. Create with `{ "key": "navigation", "value": { "home": "/site" } }`; update with `{ "value": { "home": "/site" } }`.

## Permissions and behavior

- Signed-in staff (`admin`, `editor`, `publisher`) can read content, contacts, enquiries, asset metadata and settings. Authenticated Father sessions cannot access CMS endpoints; the profile endpoints let Fathers read and update only their own account. Only admins can read or manage team accounts.
- Editors can create/edit draft content and private contacts and upload draft media. Publishers/admins approve publication. Editors cannot modify already-published content or approved contacts.
- Publishers/admins can create/update enquiries and update asset metadata. Public enquiry submission remains available at `POST /public/inquiries` with explicit consent.
- Only admins can delete resources or change settings and accounts.
- Accounts cannot delete, disable or demote themselves. Account changes are serialized to preserve at least one active administrator. Disabled/deleted accounts lose API access on their next request; changed roles apply immediately.
- User deletion clears uploaded-by attribution and preserves content. Existing foreign keys clear creator/updater/audit attribution. Password hashes are never returned.
- Sensitive content still requires verification before publication. Public contacts require approval and a verification date. Published media requires confirmed rights and nonempty alt text.
- Asset deletion removes its metadata and disk file. A failed database deletion restores the staged file. Existing content URLs pointing to a deleted asset will return 404; update those content records before deleting assets they use.
- Calendar dates retain their `YYYY-MM-DD` values without timezone shifts.
- Audit records are generated by mutations and are intentionally not editable or deletable through CRUD endpoints.

## Examples

Create a contact:

```json
{"name":"Office Contact","email":"office@example.org","approved_for_public":false}
```

Partially update a contact:

```json
{"phone":"021-0000000"}
```

Create a team account:

```json
{"name":"Content Editor","email":"editor@example.org","password":"use-a-unique-strong-password","role":"editor"}
```

Disable an account with PATCH:

```json
{"active":false}
```

## Verification

Run the seed tests from `api/` with `npm test`. Integration tests are opt-in and use a disposable database whose name must begin `omi_crud_test_`:

```sh
createdb omi_crud_test_manual
TEST_DATABASE_URL=postgres://localhost/omi_crud_test_manual npm test
dropdb omi_crud_test_manual
```

Use a fresh database on each run. The integration suite initializes it, starts a separate server on an ephemeral port, uses temporary upload storage, and covers CRUD for all resources, all 13 content categories, publication gates, permissions, validation, missing records, account safeguards and file deletion. It never uses the running website's database.

These changes add backend endpoints. The current dashboard does not yet expose buttons for every newly added operation.
